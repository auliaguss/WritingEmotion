# Project: AIEmotions — Emotion-Driven Writing Prompts

## 🎯 The Game Plan
| Category | What we are doing |
| :--- | :--- |
| **Project Goal** | A writing app where prompts are short "Verb-ing + Object" phrases, each tagged with the emotion(s) it's meant to evoke. The app learns which emotions you gravitate toward and biases future prompts accordingly. |
| **Main Focus** | Swift's native Foundation Models framework generates prompts entirely on-device; drafts remain local and publishing goes through the live backend service. |
| **What we are skipping** | Server-synced bookmark and read state. Published writing content comes from the backend; bookmarks and read history stay on-device. |

*(Original sandbox goal — testing Swift's native Foundation Model integration — is still true; it's just now in service of a concrete app instead of a blank test harness.)*

## 🛠️ The Tech Setup
| Component | What we are using | Simple Explanation |
| :--- | :--- | :--- |

## 🧭 Navigation (no more tab bar)
- **`HomeView`** is the app root. Top-right toolbar icon → `ProfileView`. Center: a **Write** button, always present. In Debug builds only, a top-left ladybug icon → `TestingProfileView` (see the Testing section below); this icon does not exist in Release builds.
- **Start of day:** only Write is interactive. Tagline: *"Start writing and see where it takes you!"*
- **After the day's one writing session is done** (`User.hasWrittenToday` — see below): Write gets a hand-drawn `ScribbleOverlay` strike across it and is disabled; the tagline changes to *"Come back tomorrow to write something new!"*; a **Read** button is revealed underneath with its own tagline, *"Discover a piece written by someone else!"*
- **`ReadView`** (pushed from Read) is a pannable/zoomable corkboard of writings loaded from the live backend, excluding the current device's own posts. Shaking refreshes and reshuffles the backend feed. Tapping a note fetches its full content and opens it with a bookmark toggle and a "Read another" shortcut; bookmark/read state lives locally on `User`, keyed by the backend writing ID.
- **`ProfileView`** now also hosts what used to be separate Drafts/Published tabs, switched via an in-page **Publish (n) / Drafts (n)** segmented toggle (`PostListContent`, reused by both Profile and Read).

## ✍️ Once-per-day writing
- `User.hasWrittenToday` / `markWrittenToday()` (backed by a `lastWriteDate` timestamp, same day-boundary pattern as the daily prompts) — set the moment `Post.saveAsDraft` runs, so **either** saving a draft **or** publishing counts as "today's writing" and locks Write until the next calendar day.
- The writing flow itself (`WritingView`) matches the mockup: prompt title + shuffle link with a live `(remaining/3)` counter, a text box with an inline "Camera" attach button pinned to its bottom edge, a tip banner (plus a red "Keep writing!" nudge under the minimum), and a "Done" button that's disabled until the minimum length is met. Tapping Done surfaces a "Save for later or publish now?" confirmation overlay. Saving dismisses immediately; publishing dismisses after the configured service accepts the writing and keeps failures as local drafts for retry.

## 🧩 How it maps to the class diagram
- **User** → `Models/User.swift` (SwiftData `@Model`). `emotionProfile: [String: Int]` is the running tally PromptManager reads to bias generation. `loadDrafts()`/`loadPublished()` are filtered views over the live `posts` relationship rather than separate fetches.
- **Post** → `Models/Post.swift`. `promptUsed` is flattened into `promptVerb` / `promptFullText` / `promptEmotionData` (a durable snapshot) instead of holding a live `PromptData` reference, since prompts are ephemeral. `saveAsDraft` is a static factory (inserts + returns a new `Post`); `publish()` flips the existing draft's state.
- **PromptManager** → `Services/PromptManager.swift`. Matches the diagram's 1→3 relationship, but the 3 `PromptData` now live as persisted state on `User` (`todaysPrompts`) rather than transient state on the manager itself — needed so the set survives app relaunches for the same day. `PromptManager` is the stateless generation/mutation layer over that persisted state (`generateDailyPromptsIfNeeded`, `discardPrompt`, `generateDiscoveryPrompt`), all backed by `LanguageModelSession`.
- **PromptData** → `Models/PromptData.swift`. Kept as a plain `Codable` struct (not a SwiftData model) since it's regenerated every session — only what the user actually writes gets persisted, via the `Post` snapshot above. As of the hybrid-emotion pass, it carries two separate emotion fields rather than one: `emotionData` (freeform creative display text) and `coreEmotion` (strict backend category, stored as a `CoreEmotion` raw value string) — see `Models/CoreEmotion.swift`.

## 🔁 The emotion feedback loop (revised)

**Daily prompts, not session prompts.** `PromptManager.generateDailyPromptsIfNeeded(for:)` generates exactly 3 prompts once per calendar day and persists them on `User` (`todaysPrompts`, backed by encoded JSON + a date stamp — see `User.swift`). The screen shows **one prompt at a time** (the first of the set), not all 3 side by side.

**Shuffling deletes, it doesn't replace.** Tapping the trash icon on a prompt calls `PromptManager.discardPrompt(_:for:)`, which permanently removes it from today's set — no new prompt is generated to fill the gap. 3 → 2 → 1, and the last remaining prompt can't be discarded (the UI disables the button; the model layer also refuses the removal as a safety net). The set refreshes to a new batch of 3 the next calendar day.

**Exploration before personalization.** `User.isEmotionProfileUnlocked` is `true` once *any single emotion* has been written from 5+ times. Below that threshold, `PromptManager` explicitly asks the model for a random, broad emotional spread — the profile isn't allowed to steer anything yet, so the user gets a real tour of different feelings before the app starts narrowing in.

**Discovery button (post-unlock, once/day, only after shuffles are exhausted).** Once unlocked, the daily 3 *are* biased toward the user's top emotions as before. A separate "Discover" option only appears once `User.hasExhaustedTodaysShuffles` is true (i.e. the user has shuffled down to their last mandatory prompt) — capped at once per calendar day (`User.hasUsedDiscoveryToday` / `markDiscoveryUsedToday()`). Its generation prompt gives the model a **strict priority order**: (1) an emotion the user has *never* scored at all — the preferred outcome, and what the instruction tells the model to reach for unless it's genuinely stuck; only if that's not possible does it (2) fall back to the user's single lowest-scored emotion. The result is appended to today's set rather than replacing anything.

**Weighting still comes from writing, not just viewing.** Saving a draft or publishing calls `User.updateEmotionWeight(_:)` for each emotion tag on the prompt actually used, via `Post.saveAsDraft`. Profile tab visualizes the resulting tally as a simple bar breakdown.

**Anti-spam floor.** Save Draft / Publish are disabled until the trimmed text is at least 10 characters (`WritingView.minimumCharacterCount`), with a live counter under the editor.

## 🪞 Live profile vs. testing profile (new)

The raw `emotionProfile` tally still exists and still drives everything in the section above — that logic is unchanged. What changed is **who gets to see the raw numbers**.

- **Live (`ProfileView`)**: the emotion bar-chart is gone. In its place, `StyleSummaryCard` shows a short, personalized reflection generated by `StyleSummaryGenerator` — a second `FoundationModels` session that's handed the actual text of the writer's last 5 published posts (not just emotion labels) and asked to write 2-4 sentences of genuine, specific prose about their voice, in second person, with an explicit instruction to avoid the flat "you've been writing like X with emotions mixed in between A, B, C, and D" report-style tone. If the model is unavailable, it falls back to a softer templated line built from the top 1-2 emotions — still phrased as a reflection, not a data dump. If nothing's published yet, it shows a simple "publish your first piece" empty state instead of generating anything.
- **Testing (`TestingProfileView`, Debug-only)**: shows the original raw bar-chart (extracted, unchanged, into `EmotionPaletteView`) plus a live readout of today's daily-cycle state (written-today, prompt count, discovery-used, unlock status) and the **"Refresh the day"** button (`User.debugRefreshDay()`), which nils out `lastWriteDate`, `dailyPromptsData`/`dailyPromptsDate`, and `lastDiscoveryUseDate` in one shot — letting a dev bypass the once-per-day gates and re-trigger fresh prompt generation without waiting for the calendar to roll over. Everything under `Views/Testing/` plus `debugRefreshDay()` itself is wrapped in `#if DEBUG`, so none of it ships in Release.

## 🎭 Hybrid emotion model: strict core vs. creative flavor (new)

**The problem.** Letting the FM name whatever emotion it wants for every prompt is great for creative variety but terrible for the database — "sad", "melancholy", "gloomy", and "sorrow" all mean roughly the same thing to a human but look like 4 unrelated keys to `emotionProfile`, so no real mathematical profile can ever form. Locking the FM to a small fixed list solves that but risks making prompts feel repetitive and flattens the app's creative voice.

**The fix — split it in two, like a tactical RPG's damage types.** A tactical RPG might give an attack a wildly creative name and animation for the player to enjoy, while the underlying engine only ever tracks it as plain "Fire" or "Pierce" damage so the math stays sane. Prompts here work the same way:

| Field | What it is | Who sees it | Who reads it |
| :--- | :--- | :--- | :--- |
| `displayEmotion` / `PromptData.emotionData` | 1-2 freeform creative words, FM's choice, e.g. "wistful yearning" | The user, in the prompt UI and as chips on published posts (`PostListView`) | `StyleSummaryGenerator`, for flavor when writing the personalized reflection |
| `coreEmotion` / `PromptData.coreEmotion` | One strict category from a fixed set of 8 (`Models/CoreEmotion.swift`: joy, sadness, fear, anger, surprise, anticipation, trust, disgust) | Nobody — internal only | `User.emotionProfile` (weighting), `PromptManager` (bias lines), the unlock threshold |

**What changed to support this:**
- `Models/CoreEmotion.swift` (new) — the enum itself, marked `@Generable` (not just `Codable`/`CaseIterable`) since it's used as a property type inside `GeneratedPrompt`, a `@Generable` struct. Without that macro FoundationModels has no schema to constrain the model's output to a valid case.
- `PromptManager`'s `GeneratedPrompt` schema now asks for both fields per prompt: a `displayEmotion` string for color, and a strict `coreEmotion: CoreEmotion` for the math — see the updated instructions block.
- `Post` gained a fourth prompt-snapshot field, `promptCoreEmotion`, alongside the existing verb/fullText/emotionData trio, plus a typed `coreEmotion: CoreEmotion?` accessor.
- `Post.saveAsDraft` now calls `User.updateEmotionWeight(_:)` **once** with `prompt.coreEmotion`, instead of looping over every freeform tag in `prompt.emotions` (which used to make one post capable of bumping 1-2 different profile keys at once — no longer possible now that the tracked key-space is closed).
- `User.updateEmotionWeight(_:)` now validates its input against `CoreEmotion(rawValue:)` and silently drops anything that isn't a real case, so `emotionProfile` can never accumulate stray freeform keys again even if something upstream regresses.
- `StyleSummaryGenerator` deliberately keeps reading `post.promptEmotions` (the creative side), NOT `post.coreEmotion` — feeding the model raw enum cases like "joy"/"trust" over and over would push the personalized reflection right back toward the flat, data-report tone that feature was built to avoid. See the doc comment at the top of that file.

## ⚠️ Things worth double-checking on your machine
- `FoundationModels` requires iOS 26+ on Apple Intelligence–eligible hardware; on the Simulator or unsupported devices, `SystemLanguageModel.default.availability` won't be `.available` and the app will silently use the fallback prompt bank instead of crashing.
- If Xcode doesn't auto-link `FoundationModels`, add it manually under the target's *General → Frameworks, Libraries, and Embedded Content*.
- **Adding required properties to `@Model` classes**: any future non-optional stored property with no default value will crash `ModelContainer` creation the same way `promptCoreEmotion` did, against anyone's existing local store. Always give new required properties a default value (or make them optional) unless you're intentionally forcing a fresh install.
- `Post.attachedImageData` / `User.profilePictureData` use `@Attribute(.externalStorage)` since photos can be large — no action needed, just noting why they're not inline blobs.
- `StyleSummaryGenerator` opens its own `LanguageModelSession`, separate from `PromptManager`'s. Two sessions is intentional (different instructions/jobs), but worth knowing if you're ever profiling on-device memory/perf.
- Everything testing-related (`User.debugRefreshDay()`, the whole `Views/Testing/` folder, the ladybug icon on `HomeView`) is behind `#if DEBUG`. Double check a Release/TestFlight archive build to confirm none of it is visible — it should compile out automatically, but worth a manual check once.
- **Existing local data from before the hybrid-emotion pass**: adding `promptCoreEmotion` as a required `String` with no default caused an immediate crash on launch against any pre-existing local store — `Fatal error: Could not create ModelContainer: SwiftDataError(...loadIssueModelContainer...)` — because SwiftData's automatic lightweight migration can't backfill a required property that has no default value. Fixed by giving it a default (`var promptCoreEmotion: String = ""`); `Post.coreEmotion` already returns `nil` gracefully for that empty-string case. Any pre-existing `emotionProfile` entries keyed by old freeform words (like "nostalgia") are unaffected by this fix and still won't clean themselves up — see the note above.
